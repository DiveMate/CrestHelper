# 自动化测试指南（替代人工装 APK 测试）

## 一句话

```bash
bash at.sh          # 全量：单元测试 + 构建 APK + 真机测试
```

不再需要"装 APK → 手点 → 看到崩了 → 抓 logcat"这套人工流程。

---

## 三层测试

| 层 | 命令 | 需要手机 | 耗时 | 抓什么 |
|---|---|---|---|---|
| **L1** 单元测试 | `bash at.sh unit` | ❌ | ~60s | 减压内核数值、NDL、合并/清理规则、CSV、JSON 容错、同步计划、线协议、元数据打标（126 项） |
| **L2** 构建 | `bash at.sh build` | ❌ | ~60s | Kotlin/NDK 编译、`.so` 是否产出、**16KB 页对齐**、APK 能否打包 |
| **L3** 真机测试 | `bash at.sh device` | ✅ | ~70s | **装上打不开/白屏崩溃**、JNI 加载、真实日志解析数值、界面交互 |

L1+L2 **完全不需要手机**，每次改代码都能跑。L3 需要手机连 USB 并开「USB 调试」。

> L3 的实现方式（2026-10 起）：Gradle **只负责构建 + 安装**两个 APK，
> 测试本身用 `adb shell am instrument -w -r` 直跑。
> 原因：AGP 的 `connectedDebugAndroidTest` 在设备侧还要做一轮自己的编排，
> 实测出现过「跑到第 7 个用例后整轮挂死、既不出结果也不超时」（等了 8 分钟）；
> 同一批 19 个用例用 `am instrument` 直跑 22 秒全绿 —— 问题在编排层，不在测试代码。
> 顺带好处：`am instrument -r` 会逐条打印 `test=` / `STATUS_CODE`，挂住时能一眼看出卡在哪个用例。

## 核心价值：抓「装上打不开」

`SmokeLaunchTest` 会自动冷启动 Activity 并检查 logcat 里有没有 `FATAL EXCEPTION`。
**这正是你现在遇到的问题**。一旦崩溃，脚本会直接把堆栈打出来：

```bash
bash at.sh device     # 自动装 APK、跑测试、抓崩溃堆栈
bash at.sh crash      # 只抓当前设备上的崩溃
bash at.sh logs       # 实时跟踪 App 日志
```

### 「装上打不开」的常见根因（对照自查）

1. **ABI 不匹配** — APK 只有 `arm64-v8a`。如果你在 x86 模拟器或老设备上装，会直接闪退。
   临时解法：`adb shell getprop ro.product.cpu.abilist` 看设备支持哪些 ABI。
2. **`.so` 加载失败** — `System.loadLibrary("dcbridge")` 抛 `UnsatisfiedLinkError`。
   现在 `DiveParser` 已改为**捕获异常不崩溃**，`isAvailable=false` 时界面显示"未加载"而非闪退。
3. **minSdk 不符** — 当前 `minSdk=26`（Android 8.0）。低于此版本装不上。
4. **权限弹窗** — 首次进入自动请求 BLE 权限（Android 12+ 用 `BLUETOOTH_SCAN/CONNECT`）。
   如果卡在权限页不是 bug，点允许即可。
5. **Activity 渲染期异常** — Compose 里任何 `null` 解包都可能崩。L3 的界面测试会抓到。

> 排查崩溃时先跑 `bash at.sh crash`；设备没连上时它会直接说"没有设备"，
> 不会给出误导性结论。

## L1 测试覆盖什么（真实数据回归）

### 减压内核 `DecoTest`（16 项）
对照 Python 版 `deco.py` 的自检黄金值，**逐位锁死**：

| 场景 | 期望值 |
|---|---|
| 水面平衡 10h 后 GF99 | 0.00 |
| 30m/20min ceiling(ZHL-16C) | 1.68 m |
| 30m/20min ceiling(GF30/85) | 15.24 m |
| 30m/20min ceiling(GF50/70) | 9.73 m |
| 升到 10m 后 GF30/85 ceiling | 9.75 m |
| 30m/40min 冲顶 GF99 | 149.4% |
| 18m/15min（免减压极限内） | 无减压义务 |
| 40m/25min（超限） | 有减压义务 |

任何数值漂移都会红——**防止改代码时悄悄偏离已验证的算法**。

### 日志合并/过滤 `DiveMergerTest`（14 项）
用 CR-4 真实数据里的三个坑做回归：

- **中途升水合并** — dive#130（1 秒 / 0.29m）与 #131（2882 秒）间隔 145 秒 < 600s 阈值 → 应合并为一次
- **浅水误触** — 0.29m < 2m → 标记 `shallow`，无效
- **短时误触** — <60s → 标记 `short`，无效
- 阈值边界（恰好 600s 仍合并）、时间倒退脏数据、空输入容错

### JSON 解析 `DiveParserJsonTest`（7 项）
非法输入一律返回 null 而不崩溃：截断 JSON、`null`、`temp: null`、缺字段。

## L3 真机测试覆盖什么

### `NativeParseTest` — JNI + libdivecomputer 端到端
用**真实原始日志** `golden_dive1.bin`（CR-4 dive#1，2446 字节）验证解析链，
对拍 `dives.csv` 里的官方结果：

```
divetime=3673s  maxdepth=7.5m  tempMin=32.0C  nsamples=377
datetime=2020-11-22 12:05:04
```

数值一旦漂移 = libdivecomputer 解析或 JNI 桥接出问题。
还覆盖：空输入/全零/随机字节/**截断数据**不会导致 native 崩溃。

### `EnvScreenTest` — Compose 界面（真实数据，8 项）
底部导航四个 tab、内置 253 条数据加载完成、年份筛选切换、
「合并设置」对话框打开、「清理垃圾」对话框（含实时预览）打开、
点卡片进详情（平均深度 / 最低最高水温 / 最小安全深度）、
详情页 NDL / GF99 图表、算法切换后指标卡仍在。

### `SmokeLaunchTest` — 启动冒烟（4 项）
冷启动 + ActivityScenario 全生命周期 + 连续三次启动 + 切后台回前台，并检查 logcat FATAL。

> 用例总数：L1 **70** 项、L3 **19** 项（8 + 7 + 4）。

## 常用命令

```bash
bash at.sh unit       # 只跑单元测试（最快，60 秒，改代码后必跑）
bash at.sh build      # 只构建 APK
bash at.sh install    # 只装到手机
bash at.sh device     # 只跑真机测试（自动装 APK）
bash at.sh crash      # 抓设备上的崩溃堆栈
bash at.sh logs       # 实时日志
```

## 工作流建议

```
改 Kotlin 代码
   ↓
bash at.sh unit          ← 90 秒，不确定逻辑有没有破坏
   ↓ 通过
bash at.sh build         ← 确认还能编出 APK
   ↓
bash at.sh device        ← 手机插着才跑，抓崩溃 + 验证 .so 解析
```

**L1 每改必跑**（90 秒内出结果），L3 在提交功能前跑一次。

## 加新测试的方法

### 纯逻辑（减压、算法、数据处理）→ 加到 `test/`
```kotlin
class MyLogicTest {
    @Test
    fun `should do something`() { ... }
}
```
跑 `bash at.sh unit`，秒级出结果。

### 需要 Android 运行时（界面、权限、BLE、.so）→ 加到 `androidTest/`
```kotlin
@RunWith(AndroidJUnit4::class)
class MyFeatureTest { ... }
```
跑 `bash at.sh device`，会自动装 APK 并执行。

> ⚠️ **方法名必须用 ASCII**（JVM 不接受非 ASCII 字符名，中文测试名会编译失败）。
> 注释和断言消息可以写中文。
