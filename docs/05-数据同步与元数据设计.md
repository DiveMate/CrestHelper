# 同步与元数据设计

本文回答四个问题：**数据怎么存、同步怎么快、手表能改什么、标记怎么打**。

对应代码：`data/DiveDb.kt`、`data/DiveMeta.kt`、`sync/*.kt`。

---

## 1. 为什么改存储

旧实现是「assets CSV 只读 + 导入写另一个 CSV + 设置里存删除/合并的 id」，三个问题：

| 问题 | 具体表现 |
|---|---|
| 表达不了元数据 | 「这条为什么没显示」要靠 `SharedPreferences` 里的 id 集合反推，换个设备就丢 |
| 增量同步没法查 | 「这块表下到第几条了」要全表扫 CSV |
| 标记与数据不同步 | 用户改了合并阈值，旧的手动组字符串可能与新数据对不上 |

现在：**SQLite 是唯一真源**，CSV 只做首次启动的种子；原始 `.bin` 仍然单独落盘，
库里只存路径。这样「换算法重跑」「重新解析原始字节」永远可行。

### 表结构

```
dive        一条原始记录一行（含全部标记位）
sample      采样点（原始剖面，不含合并后拼接的剖面）
dive_group  手动合并组的元信息（成员关系在 dive.group_id 上）
watch       手表档案（序列号/固件/上次同步进度）
sync_run    每次同步的审计日志
```

`dive` 的关键列：

| 列 | 含义 |
|---|---|
| `source` | `builtin` / `file` / `watch` |
| `device_id` + `watch_index` | 手表来源的唯一键（部分唯一索引） |
| `fingerprint` | 手表 header 里的 6 字节指纹，增量同步的锚点 |
| `group_id` + `merge_kind` | 合并归属（`none`/`auto`/`manual`） |
| `filter_reason` | 自动过滤判定（`junk`/`dup`），只标记不删 |
| `user_deleted` | 用户软删除，可撤销 |
| `favorite` | 收藏（v2 新增），纯标记 |
| `gas_o2` / `gas_he` | 呼吸气氧/氦分数（v2 新增），可为 null |
| `gas_src` | 气体来源：`record`（记录自带）/ `user`（手动标注）/ NULL（未知） |
| `avg_depth_m` / `temp_max_c` / `gas_count` | 摘要（v3 新增）：入库时按采样点算一次，列表只读这几列 |
| `raw_path` | 原始字节落盘路径 |

**原始记录永远不物理删除**。所有用户操作都是改标记位，
所以「已删除 30 条」在库里仍是 30 行，随时能恢复或导出。

### 摘要与剖面分离（v3）

采样点全量约 6 万行、3 MB。如果首屏要把它们读进内存再算平均深度/水温，
数据涨到几千条时（电脑表几千条日志是常态）白屏会明显变长。
所以拆成两条通道：

| 通道 | 内容 | 何时 |
|---|---|---|
| 摘要 | `dive` 表一行的十几列 | 启动即读，一次 `SELECT`，几十毫秒出列表 |
| 剖面 | `sample` 表 | 后台分块推进（默认每批 40 条），界面拿到一份快照就重绘 |

`avg_depth_m` / `temp_max_c` / `gas_count` 是**入库时按采样点算一次**的派生列，
口径与视图里的 `DiveEntries.avgDepth` 完全一致（同一套梯形积分），
所以列表显示的平均深度和详情页剖面算出来的不会是两个数（`SummaryOnlyTest` 守住这条）。

老库（v2）的这三列是 0，首次启动时 `backfillSummaries()` 按采样点补一遍，
只 `UPDATE` 派生列，不动任何标记位、不动采样点。

### 剖面载入是分块的

`SampleCache.loadAll()` 每读完一批就换一份新快照，界面订阅后能看到
「剖面 40/253」一路往前爬，而不是卡住几百毫秒。三个细节：

1. **先读最近的**：`diveIdsWithSamples()` 按 `datetime DESC` 排序，
   用户点开前几条的概率远大于翻到 2019 年，前面几块就够用；
2. **单条兜底**：直接跳到一条老记录时 `ensure(ids)` 只查那一条（几百行、几毫秒），
   不必等全量 —— 这就是「翻到哪加载到哪」；
3. **载入期间数据变了会重来一轮**：`generation` 计数器在导入/同步/清空时 +1，
   载入结束发现版本号对不上就把这份快照标成不完整，再补一轮（最多两轮），
   避免「一边同步一边载入」时新记录要等下次冷启动才出现。

### 重同步不会抹掉用户标记

`INSERT OR REPLACE` 会整行覆盖，而手表每轮同步都会重写同一条记录。
所以入库前先读旧行的用户标记再合并（`DiveDb.insertAll` → `oldMarkers`）：

| 标记 | 合并规则 |
|---|---|
| `favorite` | 旧值为真则保留（`OR`） |
| `user_deleted` | 旧值为真则保留（`OR`） |
| `group_id` / `merge_kind` | 新值缺失时沿用旧值（手动组不会被打散） |
| `gas_*` | **旧值来源是 `user` 时旧值优先**，否则用新解析结果 |

最后一条的判据是「旧值是不是用户标的」，不是「新值是不是空的」——
手表重下时新值里一定带着 `record` 气体，只看非空会被它盖掉。
`MarksSurviveSyncTest` 把这四类标记各写了一条回归。

## 2. 同步：全量 vs 增量

CR-4 的日志是环形缓冲：写满后覆盖最旧的，**编号会重排**。
这决定了「只用编号做减法」是不安全的——必须能发现重排并退回全量。

### 增量（默认）

```
1. 读设备信息：条数 ndives、最新编号 lastIndex、固件是否 fw6
2. 读本地进度：maxIndex = 本地已同步的最大编号，fingerprint = 那条的指纹
3. 若 lastIndex > maxIndex：
     读手表上 maxIndex 那条的 header，比对指纹
     ├─ 一致   → 增量，只下 (maxIndex, lastIndex] 这几条
     └─ 不一致 → 编号被重排，退回全量
```

多读一条 header（约 260 字节）就能判定，比起「重下几十条」几乎零成本。

编号**不一定连续**（删过日志）。fw6 用 `CMD_DIVE_INDEX_PREVIOUS` 一条条往回问，
老固件直接递减。走不动（返回 0 或原地打转）立即停，避免坏设备把循环变成死循环。

### 全量

从最新一条往回走 `ndives` 步，逐条读 header 比指纹：已存在且一致就跳过，
不一致或缺失才读剖面。慢，但能发现所有异常。

### 什么情况强制全量

| 条件 | 原因 |
|---|---|
| 本地没有这块表的记录 | 首次同步 |
| `lastIndex < maxIndex` | 编号回退 = 手表清空过，从 1 重新计数 |
| `ndives < 本地条数` | 旧记录被环形缓冲覆盖 |
| `lastIndex - maxIndex > ndives` | 缺口大于存量，编号不可信 |
| 本地缺锚点指纹 / 读不到手表 header | 无法校验，不冒险 |
| 用户点「全量」 | 手动触发 |

计划器是纯函数（`SyncPlanner.plan`），上述每条规则都有单测（`SyncPlannerTest`，13 项）。

### 幂等

入库键是 `(device_id, watch_index)`：

- 同编号同指纹 → `SKIPPED`（重复同步不产生重复数据）
- 同编号不同指纹 → `UPDATED`（设备重算过的日志）
- 编号新但内容与已有记录完全一致 → `DUPLICATE`（日志被清空重排过）

单条失败不中断整轮，连续 3 条失败才中止（大概率是断连）。

## 3. 手表设置：能改什么，不能改什么

协议里 `GRP 0xB0`（设置）只暴露四条命令：日期、时间、存储、加载。
**唯一确定可写的是时间校准**，流程必须是三步：

```
CMD_SETTINGS_LOAD   (0x28)  让设备进入可写状态
CMD_SETTINGS_DATE   (0x01)  写年-2000/月/日，设备回读同字节，不一致即失败
CMD_SETTINGS_TIME   (0x03)  写时/分/秒，同样逐字节校验
CMD_SETTINGS_STORE  (0x27)  落盘
```

顺序不能改：不 STORE 就断电，时间会停在写入前。

其余设置（单位制、深度报警、采样间隔、保守度）都在固件内部，没有公开的写命令。
界面上以**能力矩阵**展示：`supported=false` 的项灰显并写明「固件未开放」，
不做假开关——真做了用户改完发现表上没变，比没有这个功能更糟。

设备信息读得到：硬件版本、软件版本（`D01.6.x` → 新指令集）、序列号、日志条数、最新编号。

## 4. 协议速查

```
包格式  [grp][cmd][dir][len][payload][csum]     csum = (sum(前 4+len) & 0xFF) ^ 0xFF
响应    grp = 请求 grp + 1，cmd / dir 原样返回
```

| 组 | 命令 | 用途 |
|---|---|---|
| `0xA0` | `01/02/03` | 硬件 / 软件 / 序列号 |
| `0xA0` | `04` | 老固件的最新日志编号 |
| `0xB0` | `01/03/27/28` | 日期 / 时间 / 存储 / 加载 |
| `0xC0` | `05/06` | 日志条数 / 最新编号（fw6） |
| `0xC0` | `07/08/09` | 首条 / 上一条 / 下一条编号 |
| `0xC0` | `02` | dive header（含长度、剖面长度、6 字节指纹） |
| `0xC0` | `03` | 剖面分片（参数：编号 + 偏移） |

header 关键偏移：`[2]` header 长度（fw6）、`[8..12]` 剖面长度 LE32、`[12..18]` 指纹。

BLE 侧三个坑：必须 `TRANSPORT_LE`（随机私有地址）、MTU 要抬到 517、
收包必须按 `len` 重组（一次 notify 只有 `mtu-3` 字节）。

## 5. 测试策略

真机调试成本高，所以把 IO 全部抽掉：

```
WatchLink（接口）
 ├── BleWatchLink    真机：GATT → 一问一答
 └── FakeWatchLink   测试：内存里按协议应答
```

于是这些都能在 JVM 里秒级验证：

- `WatchProtocolTest` —— 固定字节向量锁死组包/解包/分包重组/header 解析
- `SyncPlannerTest` —— 13 种状态（首次/增量/最新/清空/重排/缺口过大…）
- `WatchSyncTest` —— 端到端：全量 3 条 → 增量只补 2 条；全量重跑 0 新增；
  单条坏数据不拖垮整轮；清空重排后自动降级；时间校准三步下发
- `DiveDbTest` —— 元数据打标：软删除、手动组、物化幂等、手表进度、按来源清理

其中「增量只补 2 条」那条断言会直接检查**协议命令条数**：
第二次同步只允许比计划阶段多读 2 条 header。这是「快」这个需求的可测形式。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| BLE 传输层未做真机回归 | 代码按实测 GATT 参数实现，但本轮没有手表可连；首次连表时重点看 MTU 与分包 |
| 手表设置只能写时间 | 固件没开放其它写命令，需要逆向才有 |
| 采样点全量载入内存 | 几千条 × 数百点约几十 MB，暂时可接受；再大要改按需加载 |
| 无设备时无演示数据 | 设备页会明确提示「没扫到手表」，不伪造连接 |
| CR-4 老记录读不到气体 | 见 §7：v0 记录格式不存 FO2，只能靠用户标注或全局默认 |

## 7. 气体（FO2/He）：记录里到底有没有

### 实测结论：这 294 条读不到

把手上的全部原始日志跑一遍（`build/probe_gas.c`，逻辑与 JNI 桥一致）：

| 检查项 | 结果 |
|---|---|
| 记录格式版本 `data[3]` | 294/294 = `0`（v0 老格式） |
| `DC_FIELD_GASMIX_COUNT` | 294 条全部 = 0 |
| 气体切换事件 `EVENT_CHANGE_GAS` | 0 条 |
| CCR setpoint / 减压采样 `DC_SAMPLE_DECO` | 0 条 |

原因在解析器里：气体表只在遍历剖面时遇到 `EVENT_CHANGE_GAS` 才被
填进 `parser->gasmix[]`，而 v0 的剖面格式里根本没有事件描述符段。
所以**不是解析器偷懒，是记录里真的没有这个字段**。

顺带修掉一个真 bug：JNI 桥原来在 `samples_foreach` **之前**读
`DC_FIELD_GASMIX_COUNT`，永远得到 0；现在挪到之后，并且输出
`"gas":[{"o2":0.32,"he":0}]` 与逐采样的 `"g":<下标>`，
换了带气体的固件/别的表就能直接读到。

### 三层取值（`resolveGas`）

| 优先级 | 来源 | 什么时候用 |
|---|---|---|
| 1 | 用户标注（`gas_src=user`） | 详情页点「标注」，单条覆盖 |
| 2 | 记录自带（`gas_src=record`） | 新版固件 / 其它支持气体的表 |
| 3 | 全局默认（设置页） | 记录没有气体信息时的兜底 |

为什么必须落到算法里：同一深度、同一保守度（30 m / GF 50/70），
本引擎实测空气 **6 分钟**、EAN32 **9 分钟**、EAN36 **11 分钟**。
气体只当标签显示、不喂模型的话，标了也没意义
（`GasConfigTest` 有一条断言专门守这个相对关系）。

> 注：这几个绝对值比常见休闲减压表（30 m 空气约 20 分钟）保守不少，
> 是引擎标定问题，与「气体是否参与计算」无关；本节的结论只依赖相对大小。

### 减压参数：GF 两个值直接配

档位（50/70、30/85…）本质是把连续参数离散化，想要 55/75 就只能二选一。
现在设置页和详情页都是两个数字输入框：10~100、`Low ≤ High`，非法即标红不写入。
`Deco.ALGORITHMS` 仍然保留，只给「多算法对拍」那一页当离散样本用。
