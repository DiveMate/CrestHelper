# 架构设计：潜水记录管理软件（桌面 + Android）

> 基于《01-调研-libdivecomputer与Crest-CR4.md》的结论编写

---

## 1. 「有没有完整的接口？」—— 分层回答

libdivecomputer 的接口完整度，按层看差异极大：

| 层 | 有无完整接口 | 说明 |
|---|---|---|
| 设备发现 / 描述 | ✅ 完整 | `dc_descriptor_iterator` + `dc_descriptor_filter`，能按 BLE 名自动认出 Crest-CR4 |
| 传输（串口/USB/经典蓝牙） | ✅ 完整 | 内置，但 **BLE 没有**，必须自建 |
| 设备协议（命令/封包/下载/指纹增量） | ✅ 完整 | `dc_device_open` / `dc_device_foreach` / `dc_device_set_fingerprint` / `dc_device_timesync` |
| 数据解析（字段 + 逐秒采样 + 事件） | ✅ 完整且丰富 | `dc_parser_get_field` / `dc_parser_samples_foreach`，覆盖深度/温度/NDL/减压/CNS/GF/报警 |
| **减压算法计算** | ❌ 没有 | 它只告诉你「表用了 ZHL-16C + GF 30/85」，**不会替你算** |
| 存储 / 数据模型 | ❌ 没有 | 自己设计 |
| UI / 报表 / 图表 | ❌ 没有 | 自己设计 |
| 风险分析 / 日志合并 / 过滤 | ❌ 没有 | 自己设计 |

**结论**：libdivecomputer 是一个**完整且好用的「设备接入层」**，仅此而已。它给你的是「把原始字节变成结构化剖面」的能力，上层全部要自建。好消息是：这个接入层恰恰是最难、最脏、最需要逆向的那部分，它已经替你做好了。

## 2. 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│  UI 层（桌面 / Android / 可选 Web）                          │
│  Flutter：日志列表、剖面图、报表、风险面板、设置、导入导出      │
├─────────────────────────────────────────────────────────────┤
│  应用层（Dart）                                               │
│  数据仓库、SQLite、同步、报表渲染、图表、导出(UDDF/CSV/PDF)    │
├─────────────────────────────────────────────────────────────┤
│  领域核心（Rust crate: divelog-core）★ 跨平台共享 ★           │
│  ├─ dcbridge：libdivecomputer FFI + BLE 传输层               │
│  ├─ deco   ：ZHL-16C+GF / ZHL-8 / VPM-B / RGBM近似 / DCIEM   │
│  ├─ profile：剖面预处理（重采样、平滑、分段、水面段识别）      │
│  ├─ merge  ：日志合并（中途升水再下水）                       │
│  ├─ filter ：无效日志过滤                                     │
│  ├─ risk   ：风险规则引擎（可插拔规则集）                     │
│  └─ report ：统计聚合                                        │
├─────────────────────────────────────────────────────────────┤
│  平台层                                                       │
│  Windows: btleplug(WinRT) │ Android: btleplug(JNI) 或 Kotlin  │
└─────────────────────────────────────────────────────────────┘
```

**为什么把核心放 Rust 而不是 Dart**：
- 减压算法 + 风险分析是 CPU 密集（16 组织 × 逐秒积分 × 多条潜水 × 多算法），Dart 太慢。
- libdivecomputer 是 C 库，Rust 通过 `cc` crate 直接编译链接，比 Dart FFI 处理阻塞回调简单一个数量级（`dc_custom_open` 的 read 回调要**阻塞等 notify**，在 Rust 里就是 `Condvar::wait_timeout`，在 Dart 里会死锁事件循环）。
- 同一份 Rust 代码编译到 Windows / Android / iOS / macOS，桌面端和移动端共用同一套算法，杜绝「两端算出来不一样」。

## 3. 技术选型

### 3.1 候选方案对比

| 方案 | 桌面+移动一套代码 | BLE 难度 | libdivecomputer 集成 | 生态/开发效率 | 评价 |
|---|---|---|---|---|---|
| **A. Flutter(UI) + Rust(core) + flutter_rust_bridge** | ✅ | 中（btleplug） | ✅ cc/bindgen 直编 | 高 | **推荐** |
| B. Flutter + 平台原生插件（Android Kotlin / Win C++WinRT） | ✅ | 高（写两套原生） | ✅ | 中 | 备选，BLE 更可控但要写两份 |
| C. Kotlin Multiplatform + Compose | ✅ | 高（桌面端 JVM BLE 无成熟方案） | 需 CInterop | 中 | 桌面 BLE 是硬伤 |
| D. Qt/C++（Subsurface 路线） | ✅ | 中（QtBluetooth） | ✅ 天然 | 中（C++ 开发慢） | 成熟但重，UI 迭代慢 |
| E. Electron + 独立安卓 App | ❌ 两套 | 高 | 需 node-gyp | 高 | 维护两份，不推荐 |

### 3.2 推荐：方案 A

```
Flutter 3.x (Dart)
  └─ flutter_rust_bridge v2  →  divelog-core (Rust, cdylib + staticlib)
                                   ├─ libdivecomputer (C, 通过 cc crate 编译)
                                   ├─ btleplug 0.13 (BLE)
                                   └─ 自研算法模块
存储：SQLite（桌面 sqflite_common_ffi / Android sqflite）
图表：fl_chart 或自绘 CustomPaint（剖面图要支持缩放到秒级，自绘更可控）
报表：PDF 用 pdf 包 + 自绘剖面图；表格导出 CSV/XLSX
```

**关键风险与对策**

| 风险 | 对策 |
|---|---|
| btleplug 在 Android 需要 hybrid Rust/Java build（cargo-ndk + jni-utils aar + proguard 规则），配置繁琐 | 退路：Android 端 BLE 用 **Kotlin 原生**实现扫描/GATT，通过 JNI 把字节流推进 Rust core 的 rx 队列；Rust core 只管协议和解析 |
| Windows BLE 权限/配对 | 桌面端用 WinRT，需在 manifest 声明 bluetooth 能力；CR-4 一般无需配对码 |
| CR-4 GATT UUID 未知 | 用 `tools/cr4_probe.py` 实测拿到后硬编码，避免启发式误判 |
| libdivecomputer 是 LGPL-2.1 | **动态链接**即可（cdylib），不传染你的应用代码；不要静态链进闭源产物 |
| 构建链 | ⚠️ **当前机器缺 VS Build Tools**（`C:\Program Files\Microsoft Visual Studio` 不存在，只有 MinGW gcc）。Windows 桌面端走 Rust+Flutter 需要 MSVC 工具链 → 需装「Visual Studio Build Tools 2022 + C++ 桌面开发」。Android 端用 `cargo-ndk`（Clang）不受影响。装好后 `cc` crate 直接编译 libdivecomputer，**不需要 autotools/make/cmake** |

## 4. 数据模型（SQLite）

```sql
-- 潜水（一次「记录」；可能是合并后的）
CREATE TABLE dive (
  id             INTEGER PRIMARY KEY,
  device_serial  TEXT,             -- 电脑表序列号
  dive_number    INTEGER,          -- 表内编号
  fingerprint    BLOB,             -- 6 字节，来自 libdivecomputer，用于增量下载去重
  start_utc      INTEGER,          -- Unix ms
  duration_s     INTEGER,
  max_depth      REAL,             -- m
  avg_depth      REAL,
  dive_mode      INTEGER,          -- OC / GAUGE / FREEDIVE / CCR
  water_type     INTEGER,          -- fresh / salt
  density        REAL,
  atmospheric    REAL,             -- bar
  temp_surface   REAL,
  temp_min       REAL,
  deco_type      INTEGER,          -- BUHLMANN / VPM / RGBM / DCIEM
  deco_gf_low    INTEGER,          -- 表上实际设置的 GF
  deco_gf_high   INTEGER,
  conservatism   INTEGER,
  site_id        INTEGER,
  is_merged      INTEGER DEFAULT 0,-- 是否是「升水再下水」合并出来的
  is_valid       INTEGER DEFAULT 1,-- 过滤结果
  invalid_reason TEXT,
  raw_blob       BLOB              -- 保留 libdivecomputer 原始 blob，可随时重解析
);

-- 逐秒采样
CREATE TABLE sample (
  dive_id INTEGER, t_ms INTEGER, depth REAL, temp REAL,
  cns REAL, ndl INTEGER, tts INTEGER, ceiling REAL,
  stop_depth REAL, gasmix_idx INTEGER, ppo2 REAL, setpoint REAL,
  PRIMARY KEY(dive_id, t_ms)
);

-- 事件（报警 / 书签 / 停留 / 气体切换）
CREATE TABLE dive_event (
  id INTEGER PRIMARY KEY, dive_id INTEGER, t_ms INTEGER,
  type INTEGER, flags INTEGER, value INTEGER
);

-- 气体
CREATE TABLE gasmix (
  dive_id INTEGER, idx INTEGER, o2 REAL, he REAL, n2 REAL, usage INTEGER
);

-- 合并来源：一次合并潜水由哪些原始段组成
CREATE TABLE dive_segment (      -- 用于「中途升水又下水」的合并
  id INTEGER PRIMARY KEY,
  dive_id INTEGER,               -- 合并后的 dive
  seq INTEGER,                   -- 第几段（0,1,2...）
  start_utc INTEGER, end_utc INTEGER,
  max_depth REAL, bottom_time_s INTEGER,
  source_dive_id INTEGER         -- 原始未合并的 dive（保留，可撤销合并）
);

-- 算法分析结果（缓存，支持切换算法时秒回）
CREATE TABLE analysis_run (
  id INTEGER PRIMARY KEY, dive_id INTEGER,
  algorithm TEXT,                -- 'ZHL16C','ZHL16C_GF','ZHL8','VPMB','RGBM_APPROX','DCIEM'
  params_json TEXT,              -- GF 30/85, 上升速率假设, 水面间隔等
  gf99 REAL, gf_surf REAL,       -- 关键风险指标
  ceiling_violation_s INTEGER,   -- 越过天花板的累计秒数
  first_stop_depth REAL, tts_computed INTEGER,
  cns_end REAL, otu REAL,
  result_json TEXT
);

-- 风险发现
CREATE TABLE risk_finding (
  id INTEGER PRIMARY KEY, dive_id INTEGER,
  rule_id TEXT,                  -- 'ASCENT_RATE_0_10M','MISSED_DECO_STOP',...
  severity INTEGER,              -- 0 info /1 warn /2 high /3 critical
  t_ms INTEGER, depth REAL,
  message TEXT, evidence_json TEXT
);
```

**设计要点**
- `raw_blob` 一定要留。解析器升级或算法改进后可以全量重算，不用重新连表。
- `analysis_run` 按 (dive, algorithm, params) 缓存。切换算法时不必重算全部，命中缓存直接出结果。
- `dive_segment` + `source_dive_id` 让合并**可撤销**。

## 6. 双端差异处理

| 关注点 | 桌面（Windows） | Android |
|---|---|---|
| BLE 权限 | 无需运行时权限，需 manifest 声明 | `BLUETOOTH_SCAN/CONNECT`（12+）、`ACCESS_FINE_LOCATION`（11-）、运行时动态申请 |
| 设备标识 | MAC 地址 | MAC 地址（Android 同样可用，与 iOS 不同） |
| 后台下载 | 无所谓 | 下载必须前台 + 通知栏进度，BLE 断开要能续传（用 fingerprint 增量） |
| 存储位置 | 用户目录 SQLite 文件 | App 私有目录；导出走 SAF |
| UI 形态 | 宽屏：列表 + 详情 + 分析三栏 | 窄屏：底部 tab + 详情页 |
| 图表交互 | 鼠标悬停显示逐秒数值 | 触摸拖拽游标 |
| 蓝牙栈 | WinRT（btleplug） | JNI（btleplug）或 Kotlin 原生 |

**两端同步**：一期不做云同步，用「导出 `.divelog` 单文件包（SQLite + raw blob 打包）+ 手工导入」。二期再接 WebDAV / 对象存储做自动同步。

## 7. 实施里程碑

| 阶段 | 目标 | 产出 |
|---|---|---|
| **M0 打通链路** | 用 `cr4_probe.py` 拿到 GATT UUID + 一条真实 raw blob；`dctool parse` 验证解析 | UUID 三元组 + 样例数据 |
| **M1 原生核心** | Rust `dcbridge` + BLE 传输层，CLI 能下载并打印潜水摘要 | `divelog-cli download/list/parse` |
| **M2 存储与导入** | SQLite schema + 导入管线 + 增量下载（fingerprint） | 桌面端能看到日志列表 |
| **M3 剖面可视化** | 剖面图 + 单潜详情 + 指标卡片 | 桌面端 MVP |
| **M4 分析引擎** | deco 算法 + 风险规则 + 合并 + 过滤 | 风险面板 |
| **M5 报表** | 统计/对比/年度报表 + PDF/CSV/UDDF 导出 | 报表页 |
| **M6 Android** | 移植 Flutter UI + Android BLE 权限/桥接 | 安卓端 |
| **M7 同步** | 单文件包导入导出 → 云同步 | 双端打通 |

## 8. 现在就可以开始的两件事

1. **跑 `cr4_probe.py probe`** —— 拿 GATT UUID（M0 的唯一阻塞项）。
2. **建 Rust 骨架** —— 即使没有 UUID，`dcbridge` 的 FFI 封装、`iostream.rs` 的 `dc_custom_open` 回调骨架、以及 `deco` 算法模块都可以先写，用 `cr4_probe.py download` 抓下来的 `.bin` 做离线单元测试（`dc_parser_new2` 只需要 blob，不需要真实设备）。
